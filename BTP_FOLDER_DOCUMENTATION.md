## 1. Project Overview

The `BTP` folder is a research workspace for detecting AI-generated versus human-written source code using text, image, statistical, and hybrid multimodal approaches. The project stores multiple dataset variants, preprocessing utilities, training notebooks, model checkpoints, metrics, and result exports.

The main experimental idea is to represent code in several complementary ways:

- **Raw code text**: consumed by transformer encoders such as CodeBERT, CodeT5+, and UnixCoder.
- **Code snapshots/images**: text code rendered into `.png` images, consumed by DeiT/ViT models.
- **Stylometric features**: simple hand-crafted numeric features such as line count, token count, character count, and average line length.
- **Statistical/masked-language-model metrics**: precomputed CodeBERT MLM-style metrics stored as `.npz`.
- **Fusion models**: notebooks combine two or more modalities through early fusion, late fusion, projection layers, random forests, or all-combination sweeps.

The repository is organized into three dataset branches:

- `100k/`: experiments around the H-AIRosetta/multilingual 100k-style dataset variant.
- `SO/`: Stack Overflow-style experiments, with train and ten test partitions.
- `hybrid/`: a larger mixed-language hybrid dataset built from Python, Java, and C++ CSVs.

There are also environment/cache folders:

- `venv/`: local Python virtual environment.
- `__pycache__/`: generated Python bytecode cache.

## 4. `100k/` Dataset Branch

The `100k` branch contains a multilingual/H-AIRosetta-style data pipeline and experiments. It has text files, rendered image snapshots, precomputed metric features, notebooks, and trained checkpoints.

### `100k/csvs/`

Contains the processed CSV inputs used to create text datasets.

| File | Rows | Purpose |
|---|---:|---|
| `100k/csvs/train.csv` | 792,800 | Large multilingual training CSV with columns such as `task_url`, `task_name`, `task_description`, `language_name`, `code`, `label`, and `set`. It is the source table for training text examples. |
| `100k/csvs/val.csv` | 200,999 | Large multilingual validation CSV with the same schema as train. It supports validation and split conversion. |

These CSVs contribute the original code text and labels before conversion into `text_files/`.

### `100k/text_files/`

Contains generated `.txt` files organized by split and class label.

Structure:

```text
100k/text_files/
├── train/Label_0/*.txt
├── train/Label_1/*.txt
├── valid/Label_0/*.txt
├── valid/Label_1/*.txt
├── test/Label_0/*.txt
├── test/Label_1/*.txt
├── Test_0/Label_0/*.txt
├── Test_0/Label_1/*.txt
...
└── Test_9/Label_1/*.txt
```

Each `.txt` file is one source-code sample. `Label_0` and `Label_1` are the binary classification classes. The exact semantic mapping is inherited from the source CSV label convention.

Contribution: these files are the raw text modality for transformer models and for TF-IDF/stylometric feature extraction.

### `100k/snapshots/`

Contains `.png` renderings of the corresponding files in `100k/text_files/`.

Structure mirrors `text_files/`:

```text
100k/snapshots/train/Label_0/*.png
100k/snapshots/train/Label_1/*.png
100k/snapshots/valid/Label_0/*.png
100k/snapshots/valid/Label_1/*.png
100k/snapshots/test/Label_0/*.png
100k/snapshots/test/Label_1/*.png
100k/snapshots/Test_0/Label_0/*.png
...
100k/snapshots/Test_9/Label_1/*.png
```

Each image is a code-as-image snapshot, usually black background with white rendered code text. These images let DeiT/ViT learn visual layout, indentation, density, and formatting patterns.

Contribution: image modality for `vit_only`, early-fusion, late-fusion, and mega-combination experiments.

### `100k/metrics/`

Stores precomputed numeric features in `.npz` files. These are loaded by the mega notebooks as the `metrics` modality.

| File Pattern | Arrays | Purpose |
|---|---|---|
| `metrics_train.npz` | `metrics: (5264, 5)`, `labels: (5264,)` | Metric features for the train split. |
| `metrics_valid.npz` | `metrics: (1880, 5)`, `labels: (1880,)` | Metric features for validation. |
| `metrics_test.npz` | `metrics: (2256, 5)`, `labels: (2256,)` | Metric features for unified test split. |
| `metrics_test_0.npz` ... `metrics_test_9.npz` | `metrics`, `labels` | Metric features for the ten `Test_i` partitions. |

These files are generated by `calculate_metrics.ipynb`. They likely encode masked-language-model/statistical signals such as likelihood/surprisal-style scores. Their special contribution is that they provide a compact non-neural feature source that can be combined with embeddings and images.

### `100k/checkpoints/`

Stores trained model weights and trainer states. The large files here are not source logic; they are experiment artifacts.

Main subfolders:

- `codebert_only/`: Hugging Face checkpoints for CodeBERT text-only classification. Each `checkpoint-*` folder contains files such as `config.json`, `model.safetensors`, `optimizer.pt`, `scheduler.pt`, `trainer_state.json`, `training_args.bin`, and tokenizer files where saved.
- `ct5p_only/`: CodeT5+ encoder/classification checkpoints. Contains `pytorch_model.bin`, optimizer/scheduler state, trainer state, and args.
- `vit_only/`: DeiT/ViT image-only checkpoints named `deit_epoch_1.pt`, `deit_epoch_2.pt`, and `deit_epoch_3.pt`.
- `early_fusion/`: CodeBERT + ViT early-fusion model checkpoints `fusion_epoch_*.pt`.
- `early_fusion_ct5p_encoder/`: CodeT5+ encoder + ViT fusion checkpoints.
- `early_fusion_proj/`: projection/cross-attention fusion checkpoints.
- `early_fusion_stylometric/`: fusion checkpoints that include stylometric features.

Contribution: these files preserve trained states so experiments can be resumed, evaluated, or used as components in fusion notebooks.

#### `100k/extras/file.py`

This is the main multilingual dataset builder. It:

- Parses command-line options for cache location, threshold, languages, seed, local dataset path, and output directory.
- Loads the H-AIRosetta CSV.
- Fixes randomness across Python, NumPy, PyTorch, CUDA, and Transformers.
- Splits by task rather than by individual row, preserving paired human/AI examples.
- Balances AI-generated and human-written samples within each language.
- Verifies that task pairs are complete.
- Saves per-language and multilingual train/validation CSVs.

Special contribution: it prevents leakage and broken pair structure by splitting at task level and verifying that each task has both human and AI versions.

### `.ipynb` Experiment Notebooks

Each notebook is a runnable experiment record. Most notebooks contain:

- imports and model configuration,
- dataset classes,
- path loading logic,
- training loop or Hugging Face `Trainer`,
- evaluation code,
- printed result outputs.

Their contribution is both executable research code and experiment provenance.

### `.py` Utility Scripts

Python scripts are reusable preprocessing/result-extraction helpers. Their main jobs are:

- convert CSV rows into text files,
- convert text files into image snapshots,
- organize files by label,
- compute simple stylometric features,
- parse notebook outputs into CSV/Excel reports,
- train standalone baselines.

### `.csv` Files

CSV files fall into three roles:

- source datasets containing code and labels,
- processed language/split-specific datasets,
- extracted result summaries.

Dataset CSVs contribute raw examples; result CSVs contribute reportable metrics.

### `.txt` Files

Each `.txt` file is one code sample. It is used by:

- transformer tokenizers,
- TF-IDF vectorizers,
- stylometric feature extraction,
- MLM/statistical metric generation,
- snapshot rendering.

### `.png` Files

Each `.png` file is a rendered code snapshot corresponding to a `.txt` file. It is used by ViT/DeiT image classifiers and multimodal fusion models.

### `.npz` Files

NumPy compressed arrays storing metrics and labels. These let notebooks load precomputed statistical features quickly without recomputing expensive MLM metrics.

### `.pt`, `.pth`, `.bin`, `.safetensors`

Model and optimizer artifacts:

- `.pt`/`.pth`: PyTorch checkpoints or state dictionaries.
- `.bin`: PyTorch/Hugging Face model or training argument files.
- `.safetensors`: Hugging Face model weights in the safetensors format.

These files preserve trained models and training states.

### `.json`, tokenizer files, and trainer metadata

Files such as `config.json`, `trainer_state.json`, `tokenizer_config.json`, `special_tokens_map.json`, `vocab.json`, and `merges.txt` are Hugging Face metadata. They describe model architecture, tokenizer behavior, saved training progress, and vocabulary merges.

### `.xlsx` Files

Excel reports used for human-readable result summaries. They are generated from notebook outputs or direct result parsing.

## 8. End-to-End Workflow

The project’s workflow can be read as a pipeline:

1. **Start with CSV data**
   - `100k/csvs`, `100k/extras`, `SO/csvs`, and `hybrid/csvs` contain code and labels.

2. **Convert CSV to text**
   - `text_from_csv.py` or equivalent notebook/setup logic creates label-organized `.txt` files.

3. **Render code text to images**
   - `code_to_image.py` and `generate_snapshots.py` create `.png` snapshots.

4. **Compute auxiliary numeric features**
   - stylometric functions compute simple code statistics.
   - `calculate_metrics.ipynb` creates MLM/statistical `.npz` metrics.
   - notebooks compute TF-IDF arrays on the fly.

5. **Train individual baselines**
   - CodeBERT, UnixCoder, CodeT5+, and ViT notebooks create text-only/image-only baselines.

6. **Train fusion models**
   - early fusion combines embeddings/features before classification.
   - late fusion combines predictions/confidences after classification.
   - projection/cross-attention variants test stronger fusion architectures.

7. **Run mega modality sweeps**
   - `mega*.ipynb` notebooks test all combinations of text encoder, image encoder, stylometric, TF-IDF, and metrics.

8. **Export results**
   - result utilities and Excel files summarize metrics for analysis/report writing.

## 10. Notes and Caveats

- The repository stores generated data and trained model artifacts directly. This makes it self-contained but very large.
- Many `.txt` and `.png` files are not individually meaningful beyond their split/label/sample identity; they are generated dataset items.
- Some notebooks contain historical outputs and may not represent the latest rerun unless cells are executed top to bottom.
- Some utility scripts use relative paths and assume they are run from a specific directory. For example, many scripts use paths like `../Text_Files` or `../text_files`.
- There is naming inconsistency between `Text_Files` and `text_files` across branches.
- Some notebooks have typo-like names such as `early_fusio_proj.ipynb`; the intended meaning is early fusion with projection.
- Checkpoint folders contain optimizer states that are useful for resuming training but not needed for inference-only evaluation.
